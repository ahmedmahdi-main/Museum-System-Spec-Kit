# Quickstart Validation Guide

هذا الدليل يصف كيف يتم التحقق من الميزة بعد تنفيذها. لا يحتوي كوداً تنفيذياً، بل سيناريوهات تشغيل وقبول يجب أن تمر قبل اعتبار المرحلة الأولى جاهزة.

## Prerequisites

- .NET 10 SDK على جهاز التطوير أو الخادم.
- PostgreSQL متاح مباشرة من Windows Server أو بيئة التطوير.
- صلاحية مستخدم Admin لإنشاء الأدوار الأولية.
- ملف Excel تجريبي يحتوي على صفوف صحيحة وصفوف مكررة وصفوف بموقع غير معروف.
- متصفح حديث يدعم الواجهة العربية RTL.

## Local Validation Flow

### 1. Build and Database Preparation

**Expected commands after implementation**:

```text
dotnet restore
dotnet build
dotnet test
```

**Expected outcome**:
- الحل يبنى دون أخطاء.
- كل اختبارات الدومين والتطبيق والتكامل تمر.
- migrations تنشئ جداول Identity والسجل والحركة والاستيراد والجرد والتدقيق.

### 2. Identity and Permissions Smoke Test

**Scenario**:
1. تسجيل الدخول كمستخدم Admin.
2. إنشاء مستخدم Storekeeper.
3. منح Storekeeper صلاحيات العرض والتسليم والاستلام فقط.
4. محاولة فتح شاشة إدارة المستخدمين بهذا المستخدم.

**Expected outcome**:
- يستطيع Storekeeper البحث والتسليم والاستلام.
- لا يستطيع إدارة المستخدمين أو اعتماد Excel.
- يظهر رفض صلاحية مفهوم دون تفاصيل تقنية.

### 3. Artifact Registry Test

**Scenario**:
1. إنشاء فئة قطع.
2. إنشاء قطعة برقم داخل الفئة وموقع خزن.
3. محاولة إنشاء قطعة ثانية بنفس الرقم داخل الفئة.
4. إنشاء قطعة بنفس الرقم داخل فئة مختلفة.

**Expected outcome**:
- القطعة الأولى تحصل على ArtifactId داخلي وMuseumNumber ظاهر.
- التكرار داخل الفئة يرفض 100%.
- الرقم نفسه مقبول في فئة مختلفة.

### 4. Search Test

**Scenario**:
1. البحث بالرقم المتحفي الكامل.
2. البحث بجزء من الرقم.
3. البحث بكلمة من الوصف.

**Expected outcome**:
- النتائج تعرض الرقم المتحفي، الحالة الحالية، الموقع أو الجهة الحالية، وآخر موقع خزن.
- البحث غير المطابق يظهر حالة فارغة مفهومة.

### 5. Delivery Test

**Scenario**:
1. اختيار قطعة داخل المخزن.
2. تسليمها إلى المصور مع اسم مستلم وغرض.
3. البحث عن القطعة بعد التسليم.

**Expected outcome**:
- تسجل حركة تسليم بتاريخ ووقت تلقائيين.
- الحالة تصبح خارج المخزن.
- الجهة الحالية واسم المستلم والغرض تظهر في التفاصيل.
- Movement history يحتفظ بالحركة.

### 6. Bulk Delivery Atomicity Test

**Scenario**:
1. اختيار قطعتين داخل المخزن وقطعة خارج المخزن.
2. محاولة تسليم المجموعة إلى المختبر.

**Expected outcome**:
- ترفض العملية كاملة.
- لا تتغير حالة أي قطعة.
- تعرض القطعة غير المؤهلة وسبب الرفض.
- تبقى بيانات الجهة والغرض في الواجهة لتسهيل إعادة المحاولة.

### 7. Return Test

**Scenario**:
1. اختيار قطعة خارج المخزن.
2. تسجيل عودتها إلى موقع خزن صالح.
3. البحث عنها وفتح سجل الحركة.

**Expected outcome**:
- الحالة تصبح داخل المخزن.
- CurrentLocationId وLastKnownStorageLocationId يتحدثان.
- حركة التسليم السابقة لا تحذف.
- تسجل حركة استلام جديدة.

### 8. Excel Import Preview/Validation/Commit Test

**Scenario**:
1. رفع ملف Excel يحتوي على صفوف صحيحة ومكررة وموقع غير معروف.
2. عرض Preview.
3. تشغيل Validation.
4. اعتماد السجلات المقبولة فقط.

**Expected outcome**:
- Preview لا ينشئ أي Artifact.
- Validation يوضح أخطاء الصفوف وأسبابها.
- Commit لا يتاح قبل validation.
- Commit ينشئ السجلات المقبولة فقط.
- محاولة commit ثانية لنفس الدفعة ترفض.

### 9. Reconciliation and Documented Correction Test

**Scenario**:
1. بدء جرد لموقع خزن.
2. إدخال قائمة تتضمن قطعة متوقعة وقطعة مفقودة وقطعة مسجلة بموقع آخر.
3. مراجعة النتائج.
4. إنشاء تصحيح موثق لتعارض مؤكد.

**Expected outcome**:
- التقرير يصنف Matched, Missing, Extra, Conflict, NeedsReview.
- الجرد لا يغير موقع القطعة تلقائياً.
- التصحيح الموثق يحدث الموقع الحالي مع سبب واضح.
- history وaudit يحتفظان بأثر الجرد والتصحيح.

### 10. Concurrency Test

**Scenario**:
1. مستخدمان يفتحان القطعة نفسها وهي داخل المخزن.
2. المستخدم الأول يسلم القطعة بنجاح.
3. المستخدم الثاني يحاول تسليمها من الشاشة القديمة.

**Expected outcome**:
- العملية الثانية ترفض بسبب تغير الحالة.
- تعرض الواجهة رسالة تطلب تحديث البيانات.
- لا تسجل حركة تسليم ثانية.

### 11. RTL Staff Usability Check

**Scenario**:
- تشغيل شاشات البحث، إنشاء القطعة، التسليم، الاستلام، الاستيراد، الجرد على عرض desktop اعتيادي.

**Expected outcome**:
- اتجاه النص والحقول RTL.
- الأزرار والرسائل لا تتداخل.
- المسارات الأساسية لا تتجاوز عدد الخطوات المحدد في الخطة.

## Deployment Validation

### Windows Server Path

**Expected approach after implementation**:
1. نشر التطبيق كـ published ASP.NET Core app.
2. ضبط connection string وبيانات Identity seed عبر إعدادات بيئة أو ملف إعدادات آمن.
3. تشغيل migrations في نافذة صيانة.
4. أخذ backup قبل أول استيراد حقيقي.
5. تشغيل smoke tests للبحث والحركة والاستيراد.

**Expected outcome**:
- النظام يعمل دون Docker.
- يمكن استعادة backup تجريبي قبل اعتماد بيانات حقيقية.

### Optional Docker Path

Docker يمكن دعمه لاحقاً للتطوير أو النشر الاختياري، لكنه ليس متطلب تشغيل ولا شرط قبول للمرحلة الأولى.
